카드로 공용 스택을 만들면 배치된 동료가 자동 행동하는 간접 전투를 중심으로 한 전략 덱빌딩 게임입니다. 플레이어가 직접 타격하기보다 배치·자원·변동폭을 설계하며 전투를 관리하도록 구성했습니다.

DESIGN CASE

전투 선택을 다음 턴과 탐사 기록까지 연결했습니다.

PROBLEM

자동 전투 안에서도 선택의 결과가 보여야 했습니다.

동료가 스스로 싸우더라도 플레이어가 구경만 한다고 느끼지 않도록, 카드·공용 스택·배치 순서를 하나의 의사결정 구조로 묶었습니다.

DECISION 01

카드는 피해가 아니라 역할별 행동 자원을 만듭니다.

플레이어가 공격·방어·지원 스택의 방향을 정하면 영혼석 동료가 자기 역할의 스택을 사용해 자동 행동합니다.

DECISION 02

행동하지 못한 턴도 다음 선택으로 이어집니다.

스택이 부족해 행동하지 못한 동료는 다음 턴 역할 스택을 얻고 진형 앞으로 이동합니다. 실패를 단순 손실이 아닌 다음 턴의 순서와 자원으로 바꿨습니다.

EXPERIENCE

전투 밖의 선택은 조사 기록으로 남습니다.

이동 경로에서 확인한 관찰을 조사관 수첩에 기록하고, 클리어와 전멸 뒤에는 런 단위 탐사 보고서로 묶는 흐름을 고도화하고 있습니다.

  1. 01경로 선택어디를 조사할지 정합니다.
  2. 02카드 사용역할별 공용 스택을 바꿉니다.
  3. 03동료 행동배치와 스택에 따라 자동 행동합니다.
  4. 04상태·자원피해와 스트레스, 보상을 정리합니다.
  5. 05기록관찰과 결과를 수첩·보고서에 남깁니다.

SYSTEM CONTEXT

담당 작업에서 중요하게 다룬 운영 문제

아래 항목은 현재 시스템의 주요 원칙입니다. 제 기여는 위의 네 담당 범위로 한정합니다.

01

중복 실행 경로

수집·분석 경로가 여러 개면 같은 입력과 기록을 중복 처리할 수 있어, 실제 운영 흐름은 하나의 대시보드 진입점으로 모았습니다.

02

GUI 응답성

연결·촬영·분석을 화면 처리와 분리하고, 결과만 GUI에 반영하는 구조로 오래 걸리는 작업이 화면을 막지 않도록 구성했습니다.

03

반복 알림

단순 임계값 초과가 아니라 상태 전이와 재확인 조건을 거쳐 Critical 이벤트를 승인하는 흐름으로 반복 알림을 줄입니다.

04

기록 일관성

GUI가 DB에 직접 쓰지 않고 API 계약을 통과하도록 분리해, 식별자와 임계값 준비 상태를 확인한 뒤 측정을 기록합니다.

IMPLEMENTATION NOTES

현장에서 바로 알아볼 수 있는 최소 구조를 선택했습니다.

01

2개 센서, 3개 상태

플로트 센서 두 개의 조합을 평상·수위 상승·경보의 세 단계로 바꿔 복잡한 수치 없이 상태를 구분했습니다.

02

현장 우선 표시

네트워크가 없어도 주변에서 바로 확인할 수 있도록 RGB LED와 간헐 부저를 1차 출력으로 사용했습니다.

03

입력 흔들림 완화

센서 접점이 짧게 흔들릴 때 경보가 빠르게 바뀌지 않도록 약 0.5초 디바운싱을 넣었습니다.

04

상태 전환 검증

ESP-IDF 5.5.4로 빌드·플래시하고 시리얼 로그와 실제 출력에서 0 → 1 → 2 → 1 전환을 확인했습니다.

동일한 방식으로 물을 투입한 비교 실험에서는 이물질이 많은 조건에서 배수가 늦고 내부 수위가 높게 유지되는 경향을 관찰했습니다. 이는 제한된 실험의 관찰이며 현장 성능이나 침수 예방 효과를 입증한 결과는 아닙니다.
